# AGENTS.md

Инструкции для ИИ-агентов, работающих в этом репозитории.

## Приоритеты

1. Корректность и отсутствие регрессий.
2. Сохранение согласованной архитектуры Monkey dev/build pipeline.
3. Простой, производительный и поддерживаемый код.
4. Минимальный расход токенов без потери важного контекста.
5. Актуальные проверки и архитектурная документация.

Экономия токенов не оправдывает непроверенные изменения, минификацию исходников или пропуск необходимого контекста.

## Порядок работы

- Всегда отвечай на русском языке.
- Не изменяй файлы без явного разрешения пользователя.
- Перед изменениями объясни цель и предложи план по спринтам. Применяй изменения после согласования.
- Все объяснения и планы выдавай в контекстное окно в формате md и держи трату окна не более чем 200 000.
- Выполняй только запрошенную задачу. Не добавляй несогласованный функционал и не исправляй посторонние проблемы.
- Не перезаписывай пользовательские изменения и не редактируй несвязанные файлы.
- Сначала изучай только относящиеся к задаче файлы. Для поиска используй `rg` и `rg --files`.
- Не читай целиком большие каталоги, сгенерированные графы, `dist/`, `node_modules/` и lock-файлы без необходимости.
- Объединяй независимые чтения и проверки. Не публикуй в чате длинные логи и содержимое файлов целиком.
- Финальный ответ должен содержать результат, изменённые файлы, выполненные проверки и реальные ограничения.

## Архитектура репозитория

- `brands/coral/*` — эксперименты Coral.
- `brands/sunmar/*` — эксперименты Sunmar.
- `special/*` — общие, небрандовые и служебные эксперименты.
- `scripts/*` — создание, выбор, dev/build запуск, валидация и обслуживание репозитория.
- `scripts/lib/*` — общая логика runner и инфраструктурных команд.
- `templates/monkey-experiment/*` — шаблон нового эксперимента.
- `utils/*` — общий публичный API, доступный через alias `@utils`.
- `test/*` — тесты общей инфраструктуры и utils.
- `docs/*` — руководства, архитектурная документация и справочники.

Каждая папка эксперимента является самостоятельным мини-проектом со своей точкой входа и внутренней структурой. Не выноси его локальную логику в `utils/` без реального повторного использования несколькими проектами.

## Архитектурные графы

В проекте есть три разных представления архитектуры. Выбирай минимальное представление, достаточное для задачи.

### Компактная карта репозитория

Команда:

```bash
npm run graph:project
```

Результат: `.architecture/project.json` и `.architecture/project.mmd`.

Используй её первой для знакомства со структурой, поиска зависимостей между областями и выбора файлов для дальнейшего чтения. Каждый эксперимент представлен одним узлом, поэтому карта экономит контекст и не раскрывает лишние внутренние детали.

### Карта отдельного эксперимента

Команда:

```bash
npm run graph:experiment -- <path-or-name>
```

Результат: `.architecture/experiments/<project>.json` и `.mmd`.

Используй её при анализе или изменении конкретного эксперимента. Карта начинается с entry-файла и показывает достижимые локальные импорты, ресурсы, npm-пакеты и зависимости от `@utils`.

### Полный аудит Graphify

Команда:

```bash
npm run graph:audit
```

Результат: `graphify-out/graph.json`.

Используй Graphify для глубокого аудита всего репозитория: поиска центральных узлов, транзитивных связей, циклов и зон широкого влияния. Не загружай весь `graph.json` в контекст без необходимости; сначала используй компактную карту или точечные команды Graphify.

Перед архитектурным анализом обнови нужную карту, если после её генерации структура проекта могла измениться. `.architecture/` и `graphify-out/` — локальные сгенерированные данные, их не нужно коммитить.

Подробное назначение инструментов описано в `docs/architecture/architecture-analysis.md`.

## Dev/build pipeline

- В проекте используется только Monkey pipeline на `vite-plugin-monkey`. Не возвращай и не создавай параллельный HTML runner или HTML build pipeline.
- Все эксперименты запускаются из корня через `npm run dev:experiment` и `npm run build:experiment`.
- Не добавляй локальные `package.json`, `node_modules` или `vite.config.*` в папки экспериментов.
- Dev и build имеют отдельные Vite-конфигурации и не должны протекать друг в друга.
- Dev использует HMR и автоматически выбирает свободный порт. Не фиксируй порт так, чтобы параллельные проекты конфликтовали.
- Build собирает userscript во временный staging, валидирует результат и только затем атомарно публикует его в `dist/`.
- Ошибка или прерывание build не должны заменять предыдущую успешную сборку.
- Не редактируй вручную `.vite-monkey-runner/` и `dist/`, если задача явно не относится к готовому артефакту.

## Эксперименты и общий код

- Создавай эксперимент через `npm run create:experiment -- <name> --brand <brand>`.
- Допустимые площадки: `coral`, `sunmar`, `both`. Entry по умолчанию — `main`.
- Стиль по умолчанию — CSS. SCSS выбирай явно через `--style scss`.
- Конфигурация эксперимента хранится в `experiment.config.json`.
- Используй alias `@utils` для корневых утилит.
- Перед созданием новой общей функции проверь публичный API `utils/index.js`.
- Не меняй `utils/`, если задача ограничена архитектурой dev/build или конкретным экспериментом.

## JavaScript

- Используй современный ESM и возможности JavaScript, поддерживаемые текущей сборкой Vite.
- Предпочитай небольшие функции с одной ответственностью, ранние возвраты и понятные имена.
- Не создавай абстракции без повторного использования или явного упрощения.
- Минимизируй обращения к DOM и избегай принудительных перерасчётов layout.
- Для частых событий используй `debounce`, `throttle` или `requestAnimationFrame`, только когда это обосновано.
- Освобождай обработчики, observers, timers и другие ресурсы при завершении жизненного цикла.
- Проверяй наличие DOM-узлов и внешних API. Повторная инициализация виджета должна быть безопасной.
- Не используй глобальное состояние, `innerHTML` с недоверенными данными и бессрочные observers без необходимости.
- Комментарии должны объяснять причину или ограничение, а не пересказывать код.

## SCSS и CSS

- Для новых экспериментов используй выбранный при создании формат. Не переписывай существующий CSS в SCSS без причины.
- Изолируй стили уникальным корневым классом или префиксом виджета.
- Используй вложенность умеренно, не глубже трёх уровней; избегай чрезмерной специфичности и `!important`.
- Используй CSS custom properties для runtime-настроек, SCSS-переменные — для compile-time вычислений.
- Учитывай адаптивность, `prefers-reduced-motion`, `:focus-visible`, hover и disabled.
- Для анимаций предпочитай `transform` и `opacity`, если изменение layout не требуется.

## HTML

- Используй семантические элементы: `button` для действий, `a` для переходов и логичную иерархию заголовков.
- Интерактивные элементы должны работать с клавиатуры и иметь доступное имя.
- Для изображений указывай корректный `alt`; для декоративных изображений используй пустой `alt`.
- Связывай `label` с полями формы и корректно используй `name`, `type`, `autocomplete` и сообщения об ошибках.
- ARIA добавляй только когда нативной семантики недостаточно.
- Не используй повторяющиеся `id`; боевые идентификаторы и классы должны иметь уникальный префикс.
- Не вставляй недоверенные данные через HTML-строки.

## Проверки

- Сначала выполняй минимальный релевантный набор проверок, затем расширяй его пропорционально риску.
- Общий JavaScript: `npm run lint`, `npm test`, при необходимости `npm run typecheck`.
- Конфигурации экспериментов: `npm run validate:configs`.
- Конкретный эксперимент: `npm run build:experiment -- <path-or-name>`.
- Dev/build инфраструктура: `npm run check:pipeline` или полный `npm run check:ci`.
- Документация и изменённые файлы: Prettier и `git diff --check`.
- Не исправляй посторонние ошибки, но сообщай о них, если они мешают проверке задачи.
